## 建议开工顺序

**为什么不按紫鸟的模块顺序抄：** 紫鸟是「环境管理 → IP 商城 → 团队 → RPA」的商业顺序；我们要先建技术护城河，因为团队/计费这些没有技术风险，随时能加，指纹做不好产品不成立。

1. **T2 指纹一致性交叉校验**（纯逻辑、可测、无外部依赖）—— 指纹自相矛盾是目前最容易被封号的点，且是启动闸门的前置。
2. **T1 SQLite 持久层** —— 不持久化，后面所有功能都没法在真实使用中验证。
3. **T3 代理健康检查真实化** —— 出口 IP 质量是紫鸟用户第一痛点。
4. **T5 真实进程启动 + 参数** —— 跑通「建环境→真浏览器打开」的最小闭环。
5. **T4 启动闸门**（指纹+IP+地理三检）—— 闭环之后立刻加安全拦截。
6. **T6 UI** —— 自己能日常使用，进入 dogfooding。
7. **T8 探针站 + T7 RPA** —— 量化反检测分数，再谈自动化。
8. 之后：账密托管（D 区高优先）→ 团队协作 → 云同步 → 手机端 → 计费。

## 我们相对紫鸟的 5 个超越点（要在产品里兑现）

1. Chromium C++ 层指纹伪造，而非 JS hook（Worker/iframe 无死角）。
2. seed 确定性指纹，升级零漂移，且可审计是否被篡改。
3. 启动前一致性闸门，宁可不启动也不拿矛盾身份去登录。
4. 账密与 Cookie 端到端加密，服务端无解密能力（紫鸟仅传输加密 + 官方托管）。
5. 链式代理 + 出口地理自动对齐 + OpenAPI/CDP 开放自动化生态。
